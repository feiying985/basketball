# 服务端进球识别（经典 CV 基线）

> 实现位置：`server/app/services/`。目标是用不依赖模型文件、可在 CI 和普通
> CPU 上运行的第一版检测器替换原来的 `StubShotDetector`，把「上传视频 → 识别
> 投篮事件」的链路真正跑通。更高精度的学习型检测器是下一步。

## 1. 总体流程

```text
视频文件
  │  OpenCV 解码 + 抽帧（默认 10 FPS）
  ▼
HSV 橙色掩码
  ├── 按帧做距离变换 → 候选球心（圆形、足够厚）
  └── 跨帧累积 → 持续存在的橙色结构 → 篮筐区域
  ▼
候选球心 → 贪心最近邻 + 匀速预测 → 球轨迹
  ▼
轨迹几何判定 → 投篮事件（命中 / 未中）
  ▼
ShotEvent[]（时间戳、原始帧号、made）
```

## 2. 为什么先用经典 CV

- **无模型下载**：不引入 Ultralytics（AGPL-3.0）或其他权重的许可风险，CI 也不
  需要 GPU。
- **可测试**：用合成视频就能覆盖解码、颜色检测、篮筐检测、跟踪和判定全链路。
- **接口稳定**：`ShotDetector` 协议不变，后续换成 YOLO/RT-DETR + ByteTrack
  时 API 和 App 不需要改。
- **先验证产品链路**：上传、后台任务、轮询、结果展示可以先用真实结果联调。

代价是对场景的假设较强，见第 7 节。

## 3. 篮筐检测

1. 每帧计算橙色掩码（默认 HSV `H 0-38, S≥70, V≥50`）。
2. 用指数加权累积得到「持续存在的橙色区域」：静止的篮筐会接近 1，快速移动
   的球权重很低。
3. 对持续掩码做闭运算后找轮廓，按以下条件筛选：
   - 宽度为画面宽度的 4%–45%；
   - 高宽比 ≤ 0.6（篮筐在画面里是横向的线/椭圆，不是竖立的人或衣服）；
   - 中心位于画面上方 80% 以内；
   - 轮廓内平均持续度 ≥ 0.5。
4. 取得分最高的区域作为篮筐开口：中心 `(cx, cy)`、宽度、厚度。

如果篮筐不是橙色/红色（例如白色篮筐），可在 App 确认视频时手动框选篮筐，
上传时以 `hoop_roi=x,y,w,h` 表单字段提交；也可以在服务端用
`BASKETBALL_HOOP_ROI=x,y,w,h` 指定归一化区域，跳过自动检测。App 的框选只对
当次分析生效，服务端环境变量则对全部请求生效。

## 4. 篮球检测

直接用轮廓会有一个关键问题：球穿过篮筐的瞬间会和篮筐的橙色连成一片，轮廓
变宽，恰好丢失最重要的几帧。

这里改用**距离变换局部极大值**：

- 球在画面里是一个「厚」的圆形区域，距离变换峰值约等于球半径；
- 篮筐是细长结构，距离变换峰值很小，会被最小半径过滤；
- 即使球和篮筐颜色相连，球心仍然是局部极大值，因此穿筐前后的球心仍可检出。

候选还需要满足画面最小边 1%–12% 的半径范围，避免把大面积橙色衣服/地板
当成球。每帧最多保留 8 个候选，交给跟踪阶段筛选。

真实夜景视频暴露了一个合成视频里没有的问题：橙色灯柱、广告海报和球员肤色
会形成半径 17–38px 的大色块，按半径排序时把真实球（r≈8px）挤出候选名额。
因此候选点还要通过**静止噪声过滤**：

- 持续掩码用第一帧初始化，之后按指数加权累积；
- 对每个候选点取半径大小的圆盘，计算圆盘内的平均持续度；
- 平均持续度 ≥ `BASKETBALL_STATIC_PERSISTENCE_THRESHOLD`（默认 0.5）说明该
  位置长期是橙色物体，直接丢弃。球在移动，持续度通常只有 0.1–0.3；短暂停留
  在弧顶也不会超过阈值。

这样静止的灯柱/海报不会再占用 8 个候选名额，真实球在夜景下也能进入跟踪。

## 5. 跟踪

`server/app/services/ball_tracking.py`：

- 对每条活动轨迹用最近两帧估计速度，预测下一帧位置；
- 候选与预测位置做贪心最近邻匹配，门限为画面宽度的 12%；
- 加入尺寸相似度惩罚，避免从篮筐碎片跳到球；
- 允许最多 5 帧丢失（约 0.5 秒），覆盖运动模糊和穿筐遮挡；
- 过滤掉轨迹点数不足、垂直移动范围小于画面高度 4% 的轨迹（静止篮筐、衣服等）。

## 6. 进球判定

`server/app/services/shot_geometry.py`。对每条轨迹：

1. 找到局部最高点（图像坐标 y 最小），要求它在篮筐上方，且**之前球在篮筐下方**；
2. 最高点之前有明显上升、之后有明显下降；
3. 最高点水平方向在篮筐附近（4 倍篮筐宽度内）；
4. 下降段与篮筐平面 `y = cy` 求交点：
   - 交点在篮筐开口内（`|x-cx| ≤ 0.85 × 半宽`）且继续下落 → **命中**；
   - 交点在篮筐附近（`≤ 1.8 × 半宽`）但不在开口内 → **未中**；
   - 先碰筐弹回（交点后又回到篮筐上方）→ **未中**；
5. 没有穿过篮筐平面、但在筐口高度附近达到最近距离并下落的球，记为**未中**；
6. 按 `BASKETBALL_SHOT_COOLDOWN_SECONDS`（默认 1.5 秒）合并重复事件；
   同一时间窗口内同时有命中/未中时，优先保留命中。

输出时间戳取穿过篮筐平面（或未中时最近筐点）的时刻，`frame_index` 按原始
视频帧率换算，App 可直接用它截取片段。

## 7. 已知限制

- **颜色依赖**：需要橙色篮球和橙色/红色篮筐；白色、黑色球或深色篮筐需要
  手动 ROI，或者等学习型检测器。
- **单目 2D 歧义**：从篮筐后方/侧面穿过的球可能误判；擦筐、弹框、篮筐上旋转
  的球难以稳定处理。
- **机位**：假设镜头基本固定；剧烈晃动会让持续掩码和跟踪失效。
- **只报近筐投篮**：远距离偏出、三不沾且轨迹不经过篮筐附近的球不会产生事件；
  这对「进球集锦」目标可以接受，但会低估出手数。
- **多人/多球**：当前没有球员关联，多个橙色球或橙色服装可能干扰；按轨迹筛选
  能过滤一部分，但不是完整方案。
- **性能**：CPU 上按 10 FPS 抽帧，30 秒视频通常几秒到几十秒；4K 视频会先缩到
  640 像素宽再分析。
- **合成视频验证**：仓库测试用合成视频覆盖算法逻辑，不代表真实球场准确率；
  上线前必须用真实场地视频建评估集。

## 8. 测试与调参

```bash
cd server
python -m pytest -q
```

测试包括：

- `tests/test_shot_geometry.py`：命中/未中/运球/去重/冷却的纯几何单测；
- `tests/test_ball_tracking.py`：轨迹关联、短缺口、静止目标过滤；
- `tests/test_shot_detection.py`：合成视频端到端（命中、未中、无篮筐、白色篮筐
  + ROI、运球、坏文件）；
- `tests/test_api.py`：健康检查、上传校验、完整分析任务返回真实投篮事件。

调参入口：

| 环境变量 | 作用 |
| --- | --- |
| `BASKETBALL_SAMPLE_FPS` | 抽帧率；球速快/画面大时适当提高 |
| `BASKETBALL_SHOT_COOLDOWN_SECONDS` | 同一球重复计数与连续补篮的取舍 |
| `BASKETBALL_HOOP_ROI` | 非橙色篮筐的手动区域 |
| `BASKETBALL_HUE_MIN` / `BASKETBALL_HUE_MAX` | 橙色掩码色相范围，夜景偏黄时上限可调到 40-45 |
| `BASKETBALL_SATURATION_MIN` | 最小饱和度，运动模糊掉色时可降到 45 |
| `BASKETBALL_VALUE_MIN` | 最小亮度，夜景可降到 40 |
| `BASKETBALL_BALL_MIN_RADIUS_RATIO` / `BASKETBALL_BALL_MAX_RADIUS_RATIO` | 球候选半径范围；橙色灯柱较大时把最大值降到 0.05 |
| `BASKETBALL_STATIC_PERSISTENCE_THRESHOLD` | 静止噪声过滤阈值，越低越激进 |

颜色范围、半径比例、跟踪门限等更细的参数在
`ShotDetectionConfig` / `build_tracks` 中，建议用真实评估集调整后再改默认值。
单次请求也可以在 `POST /api/v1/analyses` 的 multipart 表单里传
`hoop_roi=x,y,w,h`，覆盖部署级的 `BASKETBALL_HOOP_ROI`。
