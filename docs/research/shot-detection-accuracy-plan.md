# 进球识别精度提升方案：诊断、技术路线与验证/调参流程

> 状态：调研与方案，暂未改代码。本文把「进球识别不准」拆成可度量、可迭代的工程问题，
> 并给出需要你配合的视频采集、标注、评测与调参流程。
>
> 相关文档：[当前算法与限制](../shot-detection.md) ·
> [开源方案调研](shot-recognition.md) ·
> [部署与真实验证](../deployment-verification.md)

## 0. 结论摘要

1. **当前服务端是经典 CV 基线**：HSV 橙色掩码找球、持久化橙色区域找筐、贪心最近邻跟踪、
   2D 穿筐几何判定。链路已经跑通，但精度存在结构性上限。
2. **主要瓶颈不是再调几个参数**，而是：颜色假设太强、每帧候选名额太少、自动找筐不可靠、
   跟踪容易断、单目 2D 判定有歧义，以及**没有真实视频评估集和评测脚本**。
3. **建议路线**：先把评估集和评测脚本建起来，再按
   「经典基线增强 → 学习型球/筐检测 + 多目标跟踪 → 筐口 make/miss 分类器」分阶段升级。
   篮筐优先用「用户圈定 + 椭圆拟合」，自动找筐只作为建议。
4. **需要你配合**：第一轮拍 **15 段 10–30 秒视频**（清单见附录 A），先标注 3–5 段；
   跑通流程后再扩展到 40+ 段、100+ 个投篮事件。
5. **先定指标再调参**：建议第一目标为「命中事件精确率 ≥ 95%、召回率 ≥ 90%」，
   具体可按产品对「误报剪辑」和「漏检」的容忍度调整。

## 1. 当前算法怎么工作

实现位于 `server/app/services/`，入口是 `ShotDetector` 接口，默认 `classical` 后端。

```text
视频文件
  │ OpenCV 解码，按 10 FPS 抽帧，缩到 640 宽
  ▼
HSV 橙色掩码（H 0–38 / S≥70 / V≥50）+ 形态学去噪
  ├── 每帧距离变换局部极大值 → 圆形候选球心
  └── 跨帧指数累积 → 持续存在的橙色区域 → 自动找筐
  ▼
候选球心 → 贪心最近邻 + 匀速预测 → 球轨迹
  ▼
轨迹几何判定（顶点、上升/下降、与篮筐平面交点）→ 命中/未中
  ▼
ShotEvent[]（时间戳、原始帧号、made）+ 命中片段
```

| 阶段 | 关键实现 | 主要文件 |
| --- | --- | --- |
| 抽帧 | 默认 10 FPS，画面宽度缩到 640 | `classical_shot_detection.py` |
| 颜色掩码 | HSV 橙色范围，默认 `H 0–38, S≥70, V≥50` | `classical_shot_detection.py` |
| 找球 | 距离变换峰值；半径 1%–12% 画面短边；每帧按半径取前 8 个 | `classical_shot_detection.py` |
| 找筐 | 持续橙色区域轮廓，宽 4%–45%、高宽比 ≤0.6、位于画面上方 80%；按持续度/宽度/位置/居中打分 | `classical_shot_detection.py` |
| 跟踪 | 匀速预测 + 贪心最近邻；门限 12% 画面宽；最多丢 5 帧；过滤静止轨迹 | `ball_tracking.py` |
| 判定 | 顶点在筐上方、之前有上升、之后有下降；下降段与筐中心线求交；命中/未中/弹框 | `shot_geometry.py` |
| 配置 | 主要阈值可通过环境变量调整；更细参数在 `ShotDetectionConfig`/`build_tracks` | `config.py` |

自动找筐还有一个「置信度」保护：当第二名候选与第一名得分接近时，不猜测，
直接返回 `shots=[]` 并提示手动圈筐（`BASKETBALL_HOOP_MIN_CONFIDENCE`）。
App 确认视频时已支持手动圈定篮筐，按请求传 `hoop_roi=x,y,w,h`。

## 2. 为什么现在不准：六个结构性问题

### 2.1 颜色假设太强

当前找球完全依赖「橙色」。真实场景里：

- 夜景/灯光下白平衡偏移，球可能偏黄（H 接近或超过 38），运动模糊又会降低饱和度；
- 肤色、木质地板、橙色球衣、广告海报、灯柱都可能落进橙色范围；
- 白色、黑色或非橙色篮球直接失效；
- 同一套 HSV 阈值很难同时适配白天、夜景和室内。

这不是阈值调得不够细，而是**单靠颜色无法稳定区分球和背景**。

### 2.2 每帧只留 8 个候选，而且按半径排序

`_ball_candidates` 每帧最多保留 8 个候选，并按半径从大到小排序。真实球在 640 宽画面里
往往只有 8–15 像素半径，而灯柱、海报、球员身体会产生 17–38 像素的大色块。
即使加了静止噪声过滤，**移动的橙色干扰物仍会把真实球挤出候选名额**。
这是此前真实验证里「球没进候选」的直接原因之一。

### 2.3 自动找筐不可靠

自动找筐假设篮筐是画面里「持续存在的橙色横条」。实际场景：

- 画面里可能有多个相似橙色物体（灯柱、广告牌、橙色衣物）；
- 白色/黑色篮筐完全不满足颜色假设；
- 找到的只是外接矩形，不是真正的筐口椭圆；
- 机位稍偏、篮筐被遮挡或画面晃动时，持续掩码会失效。

所以「自动找筐 + 直接出结果」在复杂场景里风险很高。当前已经有「置信度低就要求手动圈筐」
的保护，但产品上仍应把**手动圈筐/确认**作为默认路径，而不是兜底路径。

### 2.4 跟踪太简单，轨迹容易断

`build_tracks` 用匀速预测 + 贪心最近邻，没有 Kalman 滤波、没有全局分配、没有加速度模型。
问题在于：

- 篮球在 10 FPS 下帧间位移大，抛物线运动的速度变化明显，匀速预测容易跟丢；
- 球穿过篮筐、被手/身体/网遮挡时，轨迹会断；
- 最多容忍丢 5 帧（0.5 秒），而一次投篮从出手到过筐可能 1–2 秒，遮挡后很难接回来；
- 轨迹断裂后，几何判定拿不到完整的上升/下降段，直接漏检。

### 2.5 单目 2D 几何判定有歧义

当前判定在图像平面做：球心下降时穿过 `y = 篮筐中心 y`，且横向落在筐口宽度内，就算命中。
但单目画面里：

- 球可能从篮筐**前方或后方**穿过，投影上仍会与筐口重叠；
- 擦筐、弹框、在筐上旋转的球，投影轨迹和真正穿筐很像；
- 篮筐是椭圆/有透视的，外接矩形不能准确表示筐口；
- 球有半径，球心穿过筐口不等于球整体穿过；
- 轨迹在筐口断掉时，当前逻辑要求「穿过后再往下 6 帧」才算命中，断掉就丢事件。

这些是单目 2D 的固有歧义，靠调几何阈值只能缓解，不能根治。

### 2.6 任务定义与评估缺失

- 当前只报「轨迹经过篮筐附近」的投篮，远距离偏出、三不沾不会产生事件；
  如果产品要统计命中率，**分母会偏小**，这和「进球识别」不是同一个问题。
- 没有真实视频评估集和统一指标，调参只能靠肉眼看几个片段，无法判断一次改动是变好还是变差。
- 仓库测试用的是合成视频，能覆盖逻辑，但不代表真实球场准确率。

**这是最该先补的一环**：没有度量，就没有可靠的调参和模型升级。

## 3. 可选方案对比

| 方案 | 做法 | 优点 | 缺点 | 数据需求 | 预期 | 工作量 |
| --- | --- | --- | --- | --- | --- | --- |
| A. 经典 CV 增强 | 运动门控 + 颜色/形状候选、Kalman/匈牙利跟踪、抛物线拟合、ROI 椭圆、白平衡/自适应 HSV | 不引入模型；CPU 快；可解释；可先拿一版提升 | 仍受颜色/机位限制；复杂夜景和遮挡天花板明显 | 少量标注即可调 | 中等提升 | 3–5 天 |
| B. 学习型球/筐检测 + 跟踪 | 训练 ball/rim 两类检测器；ByteTrack/OC-SORT 跟踪；轨迹穿筐判定 | 对光照、球色、背景更鲁棒；是主流路线 | 需要标注/训练；CPU 推理更慢；模型许可要注意 | 500–2000 帧 + 100+ 事件 | 明显提升 | 2–4 周 |
| C. 筐口 make/miss 分类器 | 在篮筐附近裁 1–3 秒片段，训练小型视频分类器判断是否进球；与几何投票 | 直接优化目标；对遮挡/2D 歧义更稳 | 需要进球/不进球的片段标注；可能被传球干扰 | 500–1000 段小片段 | 提升命中精度 | 1–2 周 |
| D. 音频辅助 | 检测打铁/刷网声音，与视觉投票 | 便宜；对「是否碰筐」有信息 | 户外嘈杂、手机麦克风远；不能单独用 | 少量 | 辅助 | 1–2 天 |
| E. 姿态/出手检测 | 用姿态模型识别投篮动作，切分出手事件 | 能补「远投偏出」的出手召回；可区分传球 | 计算量大；姿态标注/调参成本高 | 中等 | 对命中率统计有用 | 1–2 周 |
| F. 多视角/深度 | 第二个机位或深度相机消除 2D 歧义 | 精度最高 | 成本/部署复杂度高 | 高 | 最高 | 很高 |
| G. 端侧实时 | TFLite/NCNN 在手机端推理 | 低延迟、隐私好 | 模型小、精度受限；Android 集成成本 | 高 | 远期 | 很高 |

**推荐组合**：以 **B 为主线**，用 **A 做过渡和兜底**，在命中精度不够时叠加 **C**；
D/E 作为后续增强；F/G 暂不做。

许可提示：Ultralytics YOLO 系列（v5/v8/v11）是 AGPL-3.0，闭源商用需购买授权；
如果不想承担许可风险，优先选 YOLOX（Apache-2.0）、RT-DETR（Apache-2.0）、
NanoDet-Plus（Apache-2.0）等，或自训练后导出 ONNX。跟踪器 ByteTrack/OC-SORT/BoT-SORT
是 MIT，许可友好。如果服务端本身继续开源，AGPL 也可能可接受，但要先确认和仓库现有
MIT 许可的兼容性。

## 4. 推荐架构与分阶段计划

### 4.1 目标架构

```text
视频
  │ 抽帧（10–15 FPS，640–960 宽）
  ▼
球检测（学习型，1 类）        篮筐（用户 ROI + 椭圆拟合 / 学习型 1 类）
  │                              │
  └──────────┬───────────────────┘
             ▼
多目标跟踪（ByteTrack/OC-SORT + Kalman）
             ▼
轨迹清洗 + 抛物线拟合（RANSAC/最小二乘）
             ▼
穿筐判定（进入筐口、向下、入筐角、球半径）
             ▼
（可选）筐口小片段 make/miss 分类器 → 投票
             ▼
ShotEvent[] + 命中片段 + 诊断信息
```

设计原则：

- **接口不变**：继续用 `ShotDetector` 协议，新增 `learned` 后端，App/API 不需要改；
- **可回退**：模型缺失或推理失败时回退到 `classical`，任务不失败；
- **可解释**：结果里保留篮筐 ROI、跟踪点数、判定依据，方便排查和调参；
- **可评估**：所有后端共用同一套评估脚本和指标。

### 4.2 阶段 0：评估集与评测脚本（先做，约 1 周）

这是整个计划的地基，优先于任何算法改动。

- 定义评估集目录、清单和标注格式（见第 5 节、附录 B）；
- 实现 `server/tools/evaluate.py`：遍历视频、调用检测器、和标注对齐、输出指标和失败清单；
- 用当前 `classical` 跑出第一版基线报告，复现此前真实验证里的主要问题；
- 把「真实视频评估」和「合成视频单测」分开：CI 继续跑合成测试，真实评估手动/夜间跑。

**完成标准**：给定一个数据集目录，一条命令能输出逐视频、逐场景的
precision/recall/F1、命中/未中准确率、时间误差和失败列表。

### 4.3 阶段 1：经典基线增强（3–5 天，先拿一版提升）

不换模型也能做的改进，按优先级：

1. **篮筐默认手动圈定/确认**：App 已经支持圈筐；产品上默认让用户圈一次，
   自动找筐只作为「建议框」，用户确认后再分析。先消除「找错筐」这个最大误差源。
   同一机位/同一账号可以复用上次的 ROI，减少重复操作。
2. **候选生成改为运动 + 颜色 + 形状**：
   - 用帧差/MOG2 背景减除得到运动前景，再和橙色掩码取交集/并集；
   - 用圆度、面积、半径一致性、径向对称（radial symmetry）打分；
   - 取消「按半径取前 8」的硬截断，改为保留所有合理候选，由跟踪阶段筛选。
3. **跟踪升级**：Kalman 滤波（匀速/匀加速）+ 匈牙利分配；增大丢失容忍；
   轨迹片段按运动模型拼接；对断轨用抛物线拟合补点。
4. **轨迹判定升级**：对整条轨迹做 RANSAC 抛物线拟合，用拟合曲线求与筐口平面的交点；
   考虑球半径、入筐角、向下速度；区分擦筐/弹框；时间戳用拟合插值。
5. **颜色自适应**：先做灰度世界/白平衡归一化；从运动候选估计球的 HSV 范围；
   按场景（白天/夜景/室内）提供 profile，而不是一套全局阈值。
6. **采样与去重**：球速快时把 `BASKETBALL_SAMPLE_FPS` 提到 15–20；
   把固定 1.5 秒冷却改为「轨迹连续性 + 时间聚类」，避免把补篮合并或把一球拆成两个。

**预期**：在机位固定、篮筐可见的场景能明显改善召回；但仍受颜色和遮挡限制，
不能解决夜景/非橙色球/复杂背景。它的价值是：低成本、可解释、可作为学习型模型的兜底。

### 4.4 阶段 2：学习型检测 + 跟踪（主线，2–4 周）

1. **数据**：
   - 公开数据冷启动：Roboflow 的 basketball 数据集（约 1 万张，CC BY 4.0）等；
   - 自采数据：从你的真实视频抽帧 500–2000 张，先标 200–500 张，覆盖白天/夜景/室内、
     橙色/非橙色球、橙色/白色篮筐、遮挡、运动模糊；
   - 负样本：灯柱、海报、肤色、橙色衣物、其他球、场边杂物。
2. **模型**：ball + rim 两类检测。优先 YOLOX-nano/s 或 RT-DETR-R18（Apache-2.0），
   导出 ONNX，用 onnxruntime CPU 推理；有 GPU 再上更大模型。
   注意篮球是**小目标 + 高速运动**：640 输入可能仍然不够，优先 960 输入，
   或先按「篮筐 ROI + 前场区域」裁剪/放大再检测；也可以尝试 TrackNet 这类
   热力图跟踪方法（对小而快的球更友好，但需要自己训练）。
3. **跟踪**：ByteTrack 或 OC-SORT + Kalman；轨迹清洗、断轨拼接、抛物线拟合。
4. **篮筐几何**：检测框内做椭圆拟合，得到筐口中心、长短轴和倾角；或继续用用户 ROI。
5. **判定**：保留现有几何思路，但用拟合轨迹和椭圆筐口；可加「球在筐中」类别或
   筐口小片段分类器（阶段 3）做投票。
6. **集成**：新增 `BASKETBALL_DETECTOR=learned`；模型路径、输入尺寸、置信度阈值可配置；
   模型缺失/推理异常回退 `classical`；保留 `stub` 用于接口测试。

**预期**：在自采数据覆盖的场景里，命中召回和误报都会明显改善；代价是标注、训练和
CPU 推理时间。具体提升以评估集实测为准，不做没有数据的承诺。

### 4.5 阶段 3：精度与体验（1–2 周，按需）

- **筐口 make/miss 分类器**：在篮筐 ROI 附近裁 1–3 秒片段（进球前后），
  训练轻量视频分类器（MobileNetV3+TSM / X3D / VideoMAE-tiny），与几何判定投票；
  重点解决「球从筐前/筐后穿过」「擦筐弹框」「轨迹在筐口断掉」。
- **结果人工纠正**：结果页允许用户标记「误报/漏报」，本地保存；经用户同意后可回传作为
  评估/训练数据（这是最便宜的真实数据来源）。
- **诊断信息**：开发模式下展示篮筐框、球轨迹、候选点、置信度，方便你反馈问题。
- **按场景 profile**：白天/夜景/室内参数预设；根据画面亮度自动选择或让用户选。
- **多人和多球**：球员关联、球衣颜色过滤；优先级低于单球场景。
- **出手检测**（可选）：姿态模型识别投篮动作，补远投偏出的出手召回，用于命中率统计。

### 4.6 阶段 4：端侧实时（远期）

模型蒸馏/量化到 TFLite/NCNN，CameraX 实时推理；或「端侧检测 + 云端复核」混合。
在服务端精度稳定之前不做。

## 5. 验证与调参流程

### 5.1 数据采集（需要你配合）

**目标**：第一轮 15 段、30–60 个投篮事件；第二轮 40+ 段、100+ 事件。
每段 10–30 秒、包含 3–5 次出手，命中和未中都要有（未中很重要，否则测不出误报和召回）。

拍摄要求（第一轮尽量满足）：

1. 手机固定：三脚架/靠墙/放地上，画面不要明显晃动；手持也可以，但要单独标记。
2. 篮筐和投篮者同时入画：篮筐在画面上方，球从出手到过筐的轨迹尽量完整。
3. 1080p、30fps、MP4/H.264；不要用 4K（会缩到 640 宽）和数码变焦。
4. 一段视频只拍一个机位/一个场景；不要中途换位置。
5. 每段包含 3–5 次出手，尽量有命中也有未中；不要只拍进球。
6. 记录场景标签：白天/夜景/室内、机位（侧面/正面/斜侧/手持）、篮筐颜色、
   篮球颜色、单人/多人。
7. 画面里不要出现与篮球无关的隐私内容；如果拍到其他人，请先征得同意。
8. 视频不要提交到公开仓库；用飞书文件、私有 OSS 或私有目录传给我。

场景矩阵（第一轮 15 段，可按实际调整）：

| 场景 | 段数 | 说明 |
| --- | ---: | --- |
| 白天室外，侧面固定机位 | 3 | 基线场景 |
| 夜景室外，侧面固定机位 | 3 | 重点：灯光/白平衡/橙色干扰 |
| 室内，侧面固定机位 | 2 | 灯光稳定但可能偏黄 |
| 手持/轻微晃动 | 2 | 检验抗抖 |
| 正面/斜侧机位 | 2 | 检验 2D 歧义 |
| 白色/非橙色篮筐 + 手动圈筐 | 1 | 检验 ROI 路径 |
| 多人/遮挡/橙色衣物 | 1 | 检验干扰 |
| 非橙色篮球（如果会用） | 1 | 检验颜色假设 |

### 5.2 标注

只标「投篮事件」，不标每一帧。每段视频 2–4 分钟可标完。

字段（CSV，模板见附录 B）：

| 字段 | 说明 |
| --- | --- |
| `clip` | 视频文件名 |
| `fps` / `width` / `height` | 视频元数据 |
| `camera` | side / front / oblique / handheld |
| `lighting` | day / night / indoor |
| `shot_id` | 段内序号 |
| `release_time` | 出手时间（秒，近似即可；可空） |
| `rim_time` | 球心穿过筐口平面/最接近筐口的时间（秒，±0.3 秒） |
| `made` | 1=进球，0=未进 |
| `occluded` | 1=过筐瞬间被遮挡/出画 |
| `notes` | 擦筐、弹框、三不沾、传球经过等 |

标注要点：

- 用播放器慢放/逐帧；30fps 下 1 帧 ≈ 0.033 秒，±0.3 秒 ≈ ±9 帧；
- 「未中」也要标：包括擦筐、弹框、三不沾、偏出；传球/运球经过筐边不要标成投篮；
- 如果一段视频里没有投篮，留空即可；
- 先标 3–5 段给我校准格式，剩下的可以边跑边补；
- 可以先用当前检测器跑一遍，你在结果上改对/补漏，比从零标更快（主动学习）。

### 5.3 评测指标

把检测事件和标注事件按时间做一对一匹配（容差默认 ±1.0 秒，可配置）：

- 匹配上：TP；标注有、检测无：FN；检测有、标注无：FP。
- **事件精确率** = TP / (TP + FP)；**事件召回率** = TP / (TP + FN)；F1 为调和平均。
- **命中精确率/召回率**：只对 `made=1` 的事件算，直接对应「进球片段」质量。
- **命中/未中分类准确率**：匹配上的事件里，`made` 判断正确的比例。
- **误报率**：FP / 视频总分钟数。
- **时间误差**：匹配事件的 |检测时间 − 标注时间|，报 MAE 和 p95。
- **延迟**：分析耗时 / 视频时长，记录 CPU 型号和并发数。
- 按场景（day/night/indoor、机位）分别报；样本少时给置信区间，避免被单段视频带偏。

建议验收目标（可按产品调整，先确认再执行）：

| 指标 | 建议目标 |
| --- | --- |
| 命中事件精确率 | ≥ 95% |
| 命中事件召回率 | ≥ 90% |
| 全部投篮事件精确率 | ≥ 90% |
| 全部投篮事件召回率 | ≥ 85% |
| 命中/未中分类准确率 | ≥ 95% |
| 时间误差 p95 | ≤ 0.7 秒 |
| 误报 | ≤ 1 次 / 2 分钟视频 |
| 30 秒 1080p 分析耗时 | ≤ 60 秒（4 vCPU，实测为准） |

注意：15 段/30–60 个事件的样本量下，指标波动会很大；最终验收建议用 40+ 段、100+ 事件，
并保留一个不参与调参的测试集。

```bash

  --dataset /data/basketball-eval \
  --labels /data/basketball-eval/labels.csv \

  --config configs/night.json \

```

输出：

- 支持 `--baseline reports/...json` 对比上次结果，直接看指标涨跌。

### 5.5 调参方法

1. **先划分数据集**：按视频/场次划分 train/val/test，不能把同一段视频的相邻片段同时放进
   train 和 test；场景要分层（白天/夜景/室内都要有）。
2. **先跑基线**：当前默认参数 + 此前夜景参数各跑一遍，记录指标和失败类型。
3. **参数搜索**：经典参数用随机搜索/坐标下降，每次只改一类参数（颜色、候选、跟踪、几何），
   避免一次改太多说不清原因。
4. **按场景出 profile**：白天/夜景/室内各一组参数；根据画面亮度自动选或让用户选；
   不要用一套全局参数硬扛所有场景。
5. **学习型模型**：在 train 上训练、val 上选超参（模型大小、置信度阈值、NMS、跟踪门限），
   test 只在最后跑一次；不要用 test 调参。
6. **防过拟合**：数据少时优先选简单改动；每次改动在 val 上至少看 3 个场景；
   指标下降超过 2 个点就回退；记录每次实验的配置、数据版本、指标。
7. **回归**：固定一套「黄金集」（10–15 段），每次改动都跑；不允许命中精确率明显下降。
   在评估集不够大之前，实验参数只通过 profile/请求级覆盖，不直接改生产默认值。

### 5.6 迭代闭环

每次迭代按同一顺序：

```text
采集/补充视频 → 标注 → 跑评估 → 错误分类 → 只修最高频的一类 → 回归评估 → 记录 → 下一轮
```

错误分类建议：

| 类型 | 表现 | 优先修法 |
| --- | --- | --- |
| 找筐错误 | 篮筐框在灯柱/海报上 | 默认手动圈筐 + 椭圆拟合；自动找筐仅建议 |
| 球没检出 | 轨迹缺球、候选被挤掉 | 学习型球检测；运动候选；取消 top-8 |
| 跟踪断裂 | 过筐/遮挡后轨迹断 | Kalman/匈牙利；断轨拼接；抛物线补点 |
| 几何误判 | 从筐前/后穿过被判进；擦筐判进 | 椭圆筐口；入筐角；筐口分类器；多帧投票 |
| 重复/合并 | 一球报两次；补篮被合并 | 轨迹聚类；自适应冷却 |
| 时间偏移 | 时间戳差 1 秒 | 拟合插值；提高采样率 |
| 远投漏报 | 偏出/三不沾不报 | 姿态/出手检测（如果产品需要命中率） |

## 7. 风险与限制

- **数据少、过拟合**：15 段视频只能做方向判断，不能代表所有球场；需要逐步扩到 40+ 段。
- **场景漂移**：不同球场、灯光、机位差异大；按场景 profile + 持续采数据缓解。
- **单目 2D 歧义**：筐前/筐后穿过、擦筐弹框无法完全靠几何解决；需要椭圆/分类器/多帧投票。
- **遮挡与出画**：球被手、身体、网遮挡时轨迹会断；跟踪和拟合只能缓解。
- **相机晃动**：手持会破坏持续掩码和跟踪；第一轮先固定机位，后续加防抖/单应补偿。
- **许可**：AGPL 模型商用有传染风险；上线前确认许可或换 Apache 模型。
- **CPU 延迟**：学习型模型在 4 vCPU 上可能接近实时上限；需要实测，必要时降分辨率/抽帧/上 GPU。
- **长视频成本**：App 允许录 20 分钟，但 10 FPS 全片分析（尤其学习型模型）会很慢；
  需要先按运动/篮筐 ROI 分段，或只分析有运动的片段。
- **用户摩擦**：每次手动圈筐会增加一步操作；建议自动检测 + 用户确认，而不是完全手填。
- **隐私**：视频可能包含其他人；训练/存储需授权，公开仓库只放代码和脱敏标注。

## 附录 C：指标定义

```text
匹配：检测事件 d 与标注事件 g 时间差 ≤ 1.0s，一对一；多个候选时取最近/匈牙利分配。
TP = 匹配上的事件数
FP = 未匹配的检测事件数
FN = 未匹配的标注事件数
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
F1        = 2 * precision * recall / (precision + recall)
```

命中精确率/召回率只统计 `made=1` 的子集；命中/未中分类准确率只统计匹配上的事件。
误报率 = FP / 视频总分钟数。时间误差 = |d.time − g.time|，报 MAE 和 p95。
